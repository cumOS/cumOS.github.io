the module guide

Making KamiOS modules

A module changes how KamiOS looks, moves and sounds without a build, an install or a signature. It is one JSON file, or a zip that holds that file together with the pictures, fonts, sounds and wallpapers it names. You import it on the phone, switch it on, and switch it off again to get everything back as it was.

try it in five minutesevery knobmodule store

This guide is the whole manual for people who want to write their own. The modules that ship with the ROM are made the same way, from the same parts. KamiOS is not public yet, so some of the examples cannot be tried until the first builds are out. Everything below was written from the working system. Where something has not been looked at on a real phone, the text says so.

What a module can change

A module is a set of values and files. Nearly everything you can see, hear or feel on the phone has a place in it:

  • Look. Colours, corner radii and shapes of the quick settings, the shade, notifications, the volume panel, the lock screen shortcuts, the gesture pill, Settings and the launcher. Pictures and animations (GIF, animated WebP) in tiles, sliders, switches, the battery and the status bar. Quick settings, volume panel, Settings itself, switches and sliders.
  • Motion. The speed and easing of every animation, how the back swipe looks, how a screen opens and closes, how the phone unlocks, wakes and turns its screen off, the stack of recent apps. Animation, back swipe, lock screen.
  • Sound. The ringtone, the notification and the alarm sound, tap and keyboard clicks, locking and unlocking, charging, the low battery warning, docking, the screenshot. A module can be nothing but a sound pack. Sounds.
  • Identity. The system font and the emoji, the boot and shutdown animation, the wallpaper and lock screen, the Material You accent, the icons of apps in the launcher, the home app. Fonts and emoji, boot animation, wallpaper, accent, icons.
  • Behaviour. Options of the phone that the module writes while it is on (quick settings layout, blur, gradients, animation scale, freeform windows), and a Lua script for a different home screen, even a tiling window manager. Phone settings, Kami Shell.
  • Choices. A module can ask the user to pick a mood, a speed, a look for the back swipe, without being split into several modules. Options.

How it works

A module works in two ways, and one module can use both:

  1. Resources. Colours, sizes, corner radii, shapes and pictures that the quick settings, the shade, the volume panel, notifications, the launcher, Settings and the system read (targets). With overlays the same works for any other app, for the resource types that are safe.
  2. Settings. Options that already exist on the phone (quick settings layout, blur, animation speed, the screen off effect, the Kami Shell script, freeform windows, ...) that the module writes while it is on (settings). The old values come back when it is switched off.

On top of that a module can carry fonts, system sounds, a boot animation, wallpapers, an accent colour, launcher icons, a different home app, and a script for the Kami Shell home screen.

A module cannot run code of its own. The only code it can bring is a Lua script for Kami Shell, which runs in a sandbox with no files and no network.

Try it in five minutes

  1. Open Settings > KamiOS > Darkmoon Theme Engine > Modules and choose Export a template and the knobs. You get one file: a small module to start from, and under _knobs the complete list of what a module may set on your build.
  2. Change id, name, description and the values under targets. Delete _knobs.
  3. Copy the file to the phone and choose Import a module. The phone checks it and, if something is wrong, names the resource or the key that it refuses.
  4. Switch it on. A few things are read only when the system UI starts (the blur, the shape of a slider). Use Restart system UI at the end of the page, or put "restart": true into the module so it happens by itself.
  5. Switch it off to see the stock look again. That is the whole test cycle.

A small module:

{
  "format": "kamios-module", "version": 1,
  "id": "my-module", "name": "My module", "author": "me", "description": "What it does",
  "targets": {
    "com.android.systemui": {
      "dimen/qs_corner_radius": "12dp",
      "color/shade_panel_fallback_bg": { "day": "#FFEFEFEF", "night": "#FF101010" }
    }
  },
  "settings": { "global/window_animation_scale": 0.6 }
}

A module is one file, module.json, or a zip that has it at the top. The file says who the module is, what it changes and which choices it offers.

When several modules set the same thing, the one switched on last wins.

Targets: the knobs

targets maps a package to the resources you want to set:

"targets": {
  "com.android.systemui":      { "dimen/notification_corner_radius": "8dp" },
  "com.android.settings":      { "color/kami_page_bg": "#FF101018" },
  "com.android.launcher3":     { "dimen/kami_launch_duration_scale": 0.6 }
}

A module can only set resources that are in the list of knobs (the export gives you the list, the knob reference below explains the groups). Anything else is refused on import, with the name of the resource. This is on purpose: it keeps a module from changing things nobody expects. For other apps use overlays.

Options: choices inside a module

A module can ask the user to choose something instead of being split into several modules. Each option is a row under the module's switch. The chosen value adds its own targets and settings to the module's.

"options": {
  "background": {
    "title": "Shade background",
    "default": "bw",
    "choices": {
      "bw":    { "title": "Black and white", "targets": { "com.android.systemui": { "color/shade_panel_fallback": "#FF000000" } } },
      "monet": { "title": "Material You",     "targets": { "com.android.systemui": { "color/shade_panel_fallback": "@android:color/system_accent1_900" } } },
      "stock": { "title": "Stock shade" }
    }
  }
}

Option ids use a-z 0-9 _, choice ids a-z 0-9 - _. At most 8 options of at most 16 choices. Every choice is checked on import, not only the default. The choice is kept when the module is switched off.

A choice can also write settings, which is how one choice can switch a whole colour palette of a Kami Shell script.

Zips, pictures and other apps

A module that brings pictures, fonts, sounds or wallpapers is a zip. A module that wants to change an app that is not part of KamiOS uses overlays.

Zip modules and pictures

A module with pictures, fonts or wallpapers is a zip with module.json at the top and the files it names next to it:

my-icons.zip
 ├─ module.json
 └─ icons/airplane.png, alarm.png, ...
{
  "format": "kamios-module", "version": 1,
  "id": "my-icons", "name": "My icons", "author": "me", "description": "Round status bar icons",
  "targets": {
    "com.android.systemui": {
      "drawable/stat_sys_airplane_mode": "icons/airplane.png",
      "drawable/stat_sys_alarm": { "day": "icons/alarm.png", "night": "icons/alarm_night.png" }
    }
  }
}
  • The value of a drawable/... knob is the path of a picture inside the zip.
  • PNG, WebP, JPG or GIF, at most 2560 x 2560 px and 3 MB per file; at most 200 files and 32 MB per zip. Anything else in the zip, and any path with .. or an absolute path, is ignored or refused.
  • Vector (XML) drawables cannot be used, only pictures.
  • Import it like a JSON module. An imported module is kept in Settings' own storage; removing the module deletes its pictures.
  • Status bar icons are tinted by the system: draw them white on transparent. Any size works, they are scaled to 17 dp high. A GIF or animated WebP is not scaled: make it the size you want (about 60 px high).
  • Switching a module that has pictures restarts the system UI, because the status bar measures its icons when it starts.

Moving pictures

Many surfaces take a picture, and nearly all of them take an animated GIF or WebP too. An animation plays while its surface is on screen and stops when it is not. Some rules for all of them:

  • Keep animations small: a few hundred pixels, a few dozen frames. A tile decodes its own copy, and an animation keeps drawing, which costs battery. Use them for things you look at, not for a long reading page.
  • A picture covers its surface (centred, cropped, like a wallpaper). A small wide image does for a tile.
  • Give a picture some alpha to let the colour behind it, or the blur, show through.
  • Android blurs a whole window, not a part of one. Blur inside a single tile or slider is not possible; a translucent colour on it lets the blurred shade show through.

Overlays for any app

targets takes the knob list. overlays has the same shape but works for any package (the system UI, the launcher, a third-party app, the framework android), with resources you name yourself:

"overlays": {
  "org.example.app": {
    "color/dark_background_color": "#FF2A0A3A",
    "color/accent": { "day": "#FFFF6A00", "night": "#FFFF6A00" }
  }
}
  • Allowed: color, dimen, integer, bool and drawable (a picture in the zip, used as it is, not scaled).
  • Not allowed: text (string), and anything that names a package or a component. A module must not be able to relabel a button or redirect an app.
  • The app must be installed and must have that resource, otherwise the import is refused with its name. To find the names, look into the app's resources (for example aapt2 dump resources base.apk | grep color/).
  • Apps that read a colour from a different resource, or that have colours compiled in (Compose, code shrinking), do not change. It replaces resource values, nothing more.
  • Settings can be overlaid too. If a module makes the phone unusable, see Safety and recovery.
  • Nobody reviews modules. Switching one on shows the apps it changes and a warning, every time.

Tile sizes and layout

string/kami_qs_tile_layout gives tiles a size of their own, as a list like internet:2x1,flashlight:1x2,dnd:2x2: the name of the tile, a colon, the columns it covers, an x and the rows it covers (1 to 3). The names are the ones of the tile pictures below (internet, bt, flashlight, dnd, ...). A tile of one column shows only its symbol, wider ones show the label too, and a tile that covers several rows is centred in all of them.

Join tiles with a plus to put several of them in one cell: dnd+flashlight:2x2 is one big cell with Do Not Disturb above the flashlight (in a cell of one row they sit side by side). Each keeps its own switch.

The tiles keep their order and each cell goes to the first free place from the top left, so a tall tile leaves a gap beside it that the small tiles after it fill. A tile that is not in the list keeps its stock size, and an empty list keeps the stock grid. The tile-mosaic.json example is made for four columns. Only the panel itself changes: the edit screen still shows the stock grid.

Tile symbols

Tile symbols: the drawable/qs_<name>_icon_on and _off knobs, with the names airplane, flashlight, dnd, bluetooth, location, auto_rotate, battery_saver, hotspot, nightlight, invert_colors, light_dark_theme, data_saver. White PNGs, tinted by the tile, scaled to 24 dp high. They do not animate (the originals are animated vectors). Seen changing: airplane, auto rotate, flashlight and the Bluetooth symbol of a tile that is off. The others are untested.

Back swipe and transitions

What the screens do when you swipe back from the edge, when you open a page and when you leave it.

The back swipe

What the two screens do when you swipe back from the edge, between two apps or two screens of one app (the system draws the stock one: the screen shrinks and the one below comes up). string/kami_back_style of com.android.systemui picks the look:

ValueLook
stockthe shrinking card (default)
offnothing moves, the screen changes the moment you let go
fadethe old screen fades out and shrinks a little, the one below comes up
zoomthe old screen flies at you and fades, the new one grows into place
flipthe screen turns like a card and the new screen is its back
bookthe screen turns like a page around the edge you swiped from, the new screen is under it
spinthe screen is thrown to the side and falls away
glitchthe screen stutters, jumps and flickers into the new one

Your finger takes the animation part of the way (it follows the swipe and goes back if you cancel), letting go plays the rest. integer/kami_back_duration sets the length of that second part in milliseconds (0 takes the length of the look, 300 to 520). drawable/kami_back_overlay is a picture over both screens while it plays, centred and cropped to the display; an animated GIF or WebP moves, so a glitch, static or light leak animation makes a new look of its own. Give it some alpha to see the screens through it. integer/kami_back_overlay_alpha is how strong it is in percent, integer/kami_back_overlay_mode is 0 to show it the whole time or 1 to fade it in and out so it is strongest in the middle. The look and the picture are read again for every swipe, no restart. Not changed by this: the swipe back to the home screen, the animation that an app draws itself (some apps draw their own preview) and windows that are not full screen (freeform, split screen, letterboxed), which keep the stock look.

Going into a screen and leaving it

string/kami_open_style is how a screen of an app comes in when you open it (a sub page of Settings, the details of something), string/kami_close_style how it goes when the app finishes it (the arrow in the top bar, the back button); integer/kami_transition_duration is the length in milliseconds. They take the same names as the back swipe (stock, off, fade, zoom, flip, book, spin, glitch). Leaving plays the same poses as the back swipe; going in has looks of its own, because the new screen is on top of the old one: it zooms in, lands like a page from the right edge, or is thrown in from the side. Opening an app (a new task), dialogs and screens that bring an animation of their own keep their animation. The picture over the back swipe is not drawn here. examples/make-back-lab.py builds a module with the looks of the back swipe, of opening a page and of leaving a page as three separate choices, and a glitch animation over the swipe.

Animation speed and curves

How fast everything moves and how it speeds up and slows down.

Speed

For every animation of the system a module can set the three animation scales of the developer options: global/window_animation_scale, global/transition_animation_scale, global/animator_duration_scale. 1 is stock, 0.5 twice as fast, 0 none. The knob dimen/kami_launch_duration_scale (launcher) makes only the opening of apps from the launcher faster or slower (0.6 faster, 1.5 slower).

The framework animations (apps opening and closing, dialogs, sheets, fades) get their feel from ten easing curves and a set of durations. A module can set all of them with the target android:

A curve is SVG path data from 0,0 to 1,1, where x is the time and y the progress: M 0,0 C 0.4,0 0.2,1 1,1 is one cubic curve with two handles, and more C segments can follow. A curve that is not valid is refused on import, the system never sees it. The motion.json example has the choices snappy, smooth, bouncy and mechanical (linear). For the speed of everything at once see the three animation scales above.

Switches and sliders

The switches and sliders are the parts of Settings you touch most, so a module can restyle them completely: colours, pictures that move, a whole switch drawn by you as a strip of pictures, and how long it takes to turn. They apply to the KamiOS look of Settings (the KamiOS style switch on).

Try it

Colours and pictures

The track and the knob take a colour each for on and off. A fully transparent colour keeps the theme. The track of a switch that is on can be a picture (it may move), and the knob can show a picture of its own in place of the check mark and the cross, or none at all.

"com.android.settings": {
  "color/kami_switch_track_on": "#FFFF7A1A",
  "color/kami_switch_track_off": "#FF2A1B1B",
  "color/kami_switch_thumb_on": "#FFFFE9C4",
  "color/kami_switch_thumb_off": "#FF8A6E5E"
}

A switch as a strip of pictures

The most you can do with a switch is draw all of it yourself. A strip is one picture with frames side by side, from off (left) to on (right), 2 to 60 frames, each as high as the switch. Track and knob are part of the picture, so it can be anything: a moon that turns into a sun, a pumpkin that lights up, a lever.

  • The switch is 32 dp high. Draw at 3 times: 96 px high, and about 156 px wide for one frame. The strip may be up to 2560 px wide.
  • Corners and shape are part of the picture. Give the corners some transparency to make a pill.
  • The switch plays the strip forward when it is turned on and backward when it is turned off, and it cross-fades between two neighbouring frames, so even 8 frames look smooth.
  • The animation only plays when you touch the switch. A page that opens, or a list that scrolls, shows the right frame at once.
"com.android.settings": {
  "drawable/kami_switch_sheet": "img/switch_strip.png",
  "integer/kami_switch_sheet_frames": 16,
  "integer/kami_switch_duration": 700
}

How long a switch takes

integer/kami_switch_duration is the time in milliseconds. 0 keeps the speed of the stock switch (about 250 ms), so a module only slows its toggles down when it wants to: 500 to 900 shows every frame of a long strip. The animation keeps running when you lift your finger, and if you tap again half way it turns around from where it is.

Toggle animations

integer/kami_switch_toggle_animation moves the whole switch when you turn it: 1 pop, 2 spin, 3 jelly, 4 drop from above with a bounce. Their times stretch with kami_switch_duration as well. A switch that is a strip already moves by itself, so the toggle animation is for the plain switches.

Fonts and emoji

Fonts

A zip can change the system font:

"fonts": {
  "regular": "fonts/MyFont-Regular.ttf",
  "medium":  "fonts/MyFont-Medium.ttf",
  "bold":    "fonts/MyFont-Bold.ttf"
}
  • regular is required, medium and bold are optional (medium text uses the regular font when there is no medium one).
  • .ttf or .otf, one font per file (no .ttc), at most 10 MB each.

  • Variable fonts: a slot can be an object with the file and the axes to set. One file may serve every slot.

    "fonts": {
  "regular": { "file": "fonts/Ubuntu.ttf", "axes": { "wght": 400 } },
  "medium":  { "file": "fonts/Ubuntu.ttf", "axes": { "wght": 500 } },
  "bold":    { "file": "fonts/Ubuntu.ttf", "axes": { "wght": 700 } }
}

    Up to 4 axes per slot, tags of 4 characters (wght, wdth, opsz, ...), values from -1000 to 10000. Without axes a variable font shows its default weight in every slot.

  • The system, Settings and every app that uses the device's default font change. Apps with a font of their own do not.
  • Apps pick the font when they start: the system UI restarts when you switch the module, other apps change when you open them again (or after a reboot).
  • Fonts do not need the signature that Google's font updates carry. Only Settings can install them.
  • After the module is switched off nothing uses the files any more. adb shell cmd font clear removes all of them.
  • A font whose PostScript name equals the one of an installed font with a newer version is refused.

Emoji

A zip can replace the emoji of the whole system with another set (iOS style, WhatsApp style, Blobmoji, ...):

"emoji": "emoji.ttf"
  • One .ttf in the zip with colour glyphs (bitmaps CBDT/CBLC, COLR, sbix or SVG) and a cmap, like NotoColorEmoji.ttf. The file name has to contain emoji. It may be up to 64 MB (emoji fonts made of bitmaps are 30 MB and more), the rest of the zip up to 32 MB.
  • The font goes in front of the emoji of the ROM, which stay behind it for what it does not have (new emoji, flags). Switching the module off takes it out again; the stock emoji are back.
  • The system UI restarts when you switch the module; other apps change when they are opened again. Apps that draw their own emoji (some messengers, keyboards with their own set) keep them.
  • A font that has the PostScript name of the stock emoji font is fine: the phone gives it a name of its own when it installs it.
  • If two modules set an emoji font, the one that was switched on last wins.
  • Only Settings can install it (no signature is needed), like the fonts above.

Emoji fonts are not part of the repository: they come with the licence of the people who made them.

Sounds

A module can replace the sounds of the system, among them the ringtone, the notification and the alarm. It works as a sound pack (a module with only sounds) or as a part of a theme: sounds sits in the same file as colours, fonts and wallpapers.

"sounds": {
  "ringtone": { "file": "sounds/ring.ogg", "title": "Glass ringtone" },
  "notification": "sounds/notify.ogg",
  "touch": "sounds/tick.wav",
  "charging": "sounds/charge.ogg"
}

The value is the path of an audio file in the zip, or an object with file and a title (the name in the list of sounds; the module's name when there is none). The files are .ogg, .oga (Vorbis or Opus), .wav, .mp3, .flac or .m4a.

How it behaves:

  • The ringtone, notification and alarm are added to the sounds of the phone (they show in the list when you pick a sound, under the module's title) and set as the default ones. They go away with the module.
  • The other sounds replace the sound of the system for as long as the module is on. The switches of Settings > Sound (charging sounds, dock sounds, tap and click sounds, screen locking sound) still decide whether a sound plays.
  • Before a module sets a sound the old value is kept. It is given back when no module sets that sound any more, unless you picked another one yourself in the meantime.
  • If two modules set the same sound, the one that was switched on last wins.
  • The lock screen and the low battery warning load their sounds when the system UI starts, so the system UI restarts when you switch a module with those sounds. The others change at once.
  • The sounds are plain files: nothing runs. Keep UI sounds short; the system keeps them in memory.

What a module cannot change: the camera shutter and focus sounds (the camera app plays them itself), the dial pad tones, the volume beep and sounds that an app brings along. Apps keep their own notification sounds unless they use the system default.

Boot and shutdown animation

A module can replace the animation that plays while the phone starts, and the one that plays when it shuts down. Both are the Android boot animation format that custom ROMs have always used, so existing bootanimation.zip files work as they are.

"bootanimation": "bootanimation.zip",
"shutdownanimation": "shutdownanimation.zip"
  • Each one is the path of a zip inside the module's zip. Give both, either, or only one (the other stays as the ROM has it). The file name has to contain anim. Each zip may be up to 64 MB.
  • A plain bootanimation.zip needs no module at all. Import it in Settings > KamiOS > Darkmoon Theme Engine like a module: the phone makes a module of it, named after the file. Switch it on, and the next start shows it.

  • The animation zip has a desc.txt and folders of pictures, as always:

    720 720 30          width height fps
p 1 0 part0         play part0 once, no pause
p 0 0 part1         play part1 in a loop until the phone has started

    The pictures (part0/00000.png ...) have to be stored, not compressed (the system maps them, it does not unpack them): zip -0 -r bootanimation.zip desc.txt part0 part1. The phone refuses a zip that is compressed and says so.

  • The animation is drawn at its own size in the middle of the screen, on black (or the colour of the part line). Make it as big as the screen to fill it, or smaller to leave black around it.
  • Switching the module on only copies the zip; nothing restarts. Switching it off, or removing the module, puts the animation of the ROM back. If a zip cannot be played when the phone starts, the ROM's animation plays instead of a black screen.
  • If two modules set a boot animation, the one that was switched on last wins; the same goes for the shutdown animation.

examples/bootanimation-example.zip ("Orbit", three dots on a ring, built by examples/make-bootanimation-example.py) sets both and is a good starting point.

Preview. Open the module in the Theme Engine: a module with a boot or shutdown animation has a page with a "Preview" row for each. It plays the animation full screen on black at its real size, the way the boot animation draws it, until you tap or press back. Pictures are decoded while it plays, so a very big animation can look slower there than on the real start.

Wallpaper, accent and icons

Wallpaper and lock screen

"wallpaper": "wallpaper.jpg"
"wallpaper": { "home": "wallpaper.jpg", "lock": "lock.jpg" }

A string sets both screens, an object sets the home screen and the lock screen on their own (one of them or both). The pictures are in the zip (PNG, WebP, JPG, up to 2560 px and 3 MB; an animated one shows its first frame). Before a module sets a screen, Settings keeps what is there (a copy of the picture, the live wallpaper that was running, or "the lock screen shows the home wallpaper"). When no module sets that screen any more it is given back, unless you picked another wallpaper in the meantime. If two modules set the same screen, the last one switched on wins.

Home app

"home_app": "com.example.launcher" makes that launcher the home app while the module is on (nothing happens when it is not installed). The app that was home before comes back when the module is switched off, unless you picked another in the meantime. KamiOS ships two extra home screens you can name here: com.kami.shell (the scripted one, see below) and com.metro.launcher (a Windows Phone start screen with live tiles).

Accent colour (Material You)

The header card of Settings, the switches, the titles, the tiles that are on and every other colour that follows Material You come from one seed colour, normally taken from the wallpaper. A module can set it:

"accent": "#B56CFF",
"accent_style": "VIBRANT"

accent is the seed (#RRGGBB). accent_style is optional: TONAL_SPOT (the default), VIBRANT, EXPRESSIVE, SPRITZ, RAINBOW, FRUIT_SALAD or CONTENT. It is the same setting as Wallpaper & style, so the whole system re-colours at once, day and night. The last module that has an accent wins. When none has one any more, the old value comes back, unless you chose another colour in the meantime.

Launcher icons

A zip can give apps an icon in the launcher, like an icon pack:

"launcher_icons": {
  "com.android.deskclock": "icons/clock.png",
  "com.android.settings/com.android.settings.Settings": "icons/settings.png"
}

The key is a package, or package/Class for one activity (the activity wins over the package). Icons are used as they are (full colour, already shaped, no mask is put around them), up to 512 px. Switching the module on or off changes them straight away. Icon pack apps keep working; a module icon wins over them. This needs the KamiOS launcher.

Phone settings

A module can set the options of the KamiOS pages, the same ones that Your changes lists:

"settings": {
  "system/qs_tiles_columns": 5,

  • The key is store/key: system, secure, global, or the Lineage tables lineage_system, lineage_secure, lineage_global, then the key the page uses. The value is a number, true/false or text, like the option itself. The export of the knobs lists them all.
  • Options of the Misc page (game spoofing, integrity, sensor blocking, Tricky Store) cannot be set by a module.
  • When the module is switched on, Settings keeps the value an option had and writes the module's. Where two modules set the same option, the one switched on last wins.
  • Settings take effect at once, no restart.
  • The value of a setting can be any text, which is how a module hands a whole script to Kami Shell.

Gradients

The filled part of the volume slider, the brightness bar and the active quick settings tiles can have a gradient:

  "system/qs_brightness_slider_gradient": true,

Kami Shell: a home screen in Lua

Kami Shell is an optional home screen for KamiOS. It is drawn by a small renderer and the look, the arrangement of the icons and every animation are a Lua script that a module can replace. You can switch it on as a module (home app com.kami.shell) or choose it under Settings > Apps > Default apps > Home app. It keeps the gestures and the recents screen of the system launcher.

The built-in script is a normal home screen: pages you arrange by long press and drag, folders, widgets (clock, analog clock, date, battery, search bar, note, stopwatch, counter, year progress), an app drawer with a letter rail and search, a swipe down for notifications.

Which script runs

A module sets it with the setting secure/kami_shell_script:

  • preset:<name>: a script that ships with the app. preset:a+b loads several one after the other. Lines after the first line are Lua that runs after the presets, so a module can change a number without a script of its own:

    preset:tiling+pal-nord
wm.gap = 10
  • Or the whole Lua script as the text of the setting.

Presets: cube, wave, fan, grid-big, minimal, widgets-demo (change the pages and icons only), and tiling with the palettes pal-gruvbox, pal-catppuccin, pal-nord, pal-tokyo (a whole home screen, see the next chapter).

A script that starts with --@extend runs on top of the built-in one and only has to change cfg, fx and add widgets. Any other script replaces the built-in one entirely. If a script does not load, or frame fails twice in a row, the built-in script takes over and a message is shown. A call that runs longer than 120 ms is stopped.

Changing the built-in look

--@extend
cfg.cols = 5
function fx.page(o)            -- o: how far this page is from the one in front (-1 left, +1 right)
  return 1 - 0.3 * math.abs(o), 1 - math.abs(o), o * 20, 0, 0   -- scale, alpha, rotation, extra x, extra y (dp)
end
function fx.icon(o, col, row, cols, rows)
  return 0, 0, 1, 1, o * 30    -- extra x, extra y (dp), scale, alpha, rotation
end

cfg holds the columns, icon size, label size, spring, how dark the wallpaper is dimmed, accent, glass colour, whether the first page starts with clock and search, the dock size and the most pages.

Opening and closing apps. The window of an app grows out of its icon and falls back into it along a curve your script gives:

--@extend
-- t runs 0..1 over fx.app_duration(closing) seconds. a.x a.y a.w a.h a.radius: the icon (px); a.sw a.sh: the screen;
-- a.corner: corner radius of the screen; a.closing; a.key: the app. Return the window box (x, y, w, h), its
-- corner radius and its alpha.
function fx.app_duration(closing) return closing and 0.30 or 0.55 end
function fx.app(t, a)
  local p = a.closing and (1 - t) or t          -- 0 = at the icon, 1 = filling the screen
  p = p * p * (3 - 2 * p)
  return a.x * (1 - p), a.y * (1 - p), a.w + (a.sw - a.w) * p, a.h + (a.sh - a.h) * p,
    a.radius + (a.corner - a.radius) * p, math.min(1, p * 4)
end

The module store

Modules that other people made live in the module store. Open Settings > KamiOS > Darkmoon Theme Engine > Module store to browse them, and read what is in them before you switch one on.

Using it

  • A tap downloads a module and puts it in Your modules, switched off. You switch it on there, with the same warnings as for a module you imported yourself.
  • Nothing is fetched until you open the store. Only https is used, the sizes are limited, and what comes back is data: a module from the store can do no more than any module you import by hand.
  • An entry has a name, author, version, description, a thumbnail and screenshots (a tap on a screenshot opens it full screen). The module_version of a module is compared with the one on the phone, so the store offers an update when yours is newer.

Sharing your own

The store is a public GitHub repository, kamiosmodules/module-store, with a small website. Adding or updating a module is a pull request and needs no update of the ROM.

  1. Fork the repository and add a folder modules/<id>/. The folder name has to be exactly the id in your module.json.
  2. Put module.json at the top of that folder, with the pictures, fonts and sounds it names next to it. Fill name, author and a real one-line description, and a module_version.
  3. Optional, for the store only (they are left out of the download): thumbnail.png (a small square icon) and a screenshots/ folder with PNG, JPG, WebP or GIF files, shown in number order.
  4. Open a pull request. A maintainer looks at it; once it is merged, a GitHub Action zips the modules, publishes them and rewrites modules.json, so the module is in the store 1 to 2 minutes later.

Be careful with what you install

The maintainers look at pull requests, but that is not a security audit. A module can still restyle your system UI, set a launcher or change your wallpaper. Read what a module changes before you switch it on. Switching one on shows the apps it changes and a warning, every time.

Safety, recovery and limits

Safety

A module cannot run code, other than a Kami Shell script in its sandbox, and it can only set what the knob list, the settings of the phone and the overlay rules allow. Modules you import by hand are not reviewed by anyone, and modules from the store are only looked at, not audited. Read a module before you switch it on, and do not install every module you find on the internet.

Recovery

A module that breaks the system UI or the launcher is not permanent:

  • Modules > Turn all modules off puts everything back.
  • Safe mode turns every module off.
  • If Settings is out of reach (a crash loop of the system UI): adb shell settings delete system kami_modules_enabled, then adb shell cmd overlay list | grep com.android.settings:kami_ and adb shell cmd overlay disable --user 0 <the names>.
  • If a Kami Shell script misbehaves: adb shell settings delete secure kami_shell_script, or choose another home app.

Limits and what does not work

Pictures2560 x 2560 px, 3 MB per file, 200 files and 32 MB per zip
Fonts.ttf/.otf, 10 MB each
Sounds.ogg, .oga, .wav, .mp3, .flac, .m4a; 15 MB per file, 64 MB per zip with sounds, the length and size per slot are in the table in Sounds
Launcher iconsup to 512 px
Options8 per module, 16 choices each
Axes per font slot4
Script100 KB per kami.save table; a call longer than 120 ms is stopped
  • A module cannot run code, other than the Kami Shell script.
  • It cannot set anything that is not in the knob list (targets), is not a setting of the phone (settings), or is text or a component name (overlays).
  • It cannot change the Misc page.
  • It cannot restyle the system's own recents screen beyond the knobs above. With Kami Shell as the home app the overview can be replaced by one of your own.
  • Blur inside a single tile or a slider fill is not possible.
  • Apps that draw their colours in code, or that are not installed, do not change.
  • Colours that are system colours are taken when the module is switched on and do not follow a new wallpaper until you switch it off and on.
  • Some things are read only when the system UI starts. Restart it from the Modules page.
